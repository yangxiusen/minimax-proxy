# 架构设计

## 架构定位

系统位于外部调用方与私有 MiniMax-H3 服务之间，不是简单 URL 转发，而是带任务状态管理的协议适配层。

## 模块划分

1. API 层：路由、Bearer 鉴权、参数校验、限流与响应封装。
2. 任务服务：生成任务 ID，维护状态机、所有权和查询过滤。
3. 本地队列与调度器：维护全局 FIFO，并向健康、空闲的上游实例分配任务。
4. 上游适配器：将标准字段映射为 Gradio 参数，提交并获取 `event_id`。
5. 结果处理：轮询上游结果，绑定视频产物并记录失败原因。
6. 持久化层：使用 SQLite 保存任务、API Key 标识、幂等记录、Gallery 快照、结果 URL 映射及审计数据。

## 关键流程

`调用方 -> 鉴权/校验 -> 本地任务入队 -> 调度器 -> 私有 API -> Gallery 轮询 -> 状态持久化 -> 调用方主动查询`

## 部署与边界

- Docker 单容器运行，SQLite 文件通过 Volume 持久化。
- 多个私有 API 地址通过环境变量注入，不写死 IP。
- 每个私有实例由中转服务独占且一次只执行一个任务；通过执行前后 Gallery 快照识别新增视频。
- 对外直接返回各实例配置的 `public_base_url` 下载链接，不代理视频流量。
- 文件和任务保留 7 天后逻辑删除，不负责删除上游物理视频。
