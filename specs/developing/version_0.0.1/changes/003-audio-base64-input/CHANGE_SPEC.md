## 2. 背景与目标

调用方会把本地 WAV 或 MP3 音频编码为完整 Data URI，并写入现有 `audio_url.url` 字段。当前前置服务只接受 HTTP/HTTPS 音频 URL，因此会在任务创建阶段错误提示音频必须上传为可访问 URL。

本变更使音频输入同时支持 HTTP/HTTPS URL 和 `data:audio/...;base64,...`，并在提交私有 Gradio 服务前将 Base64 音频上传为该服务可读取的缓存文件。图片继续支持 URL 与 Base64，视频继续只支持 URL。

## 3. 兼容边界

- 音频 Data URI 仅接受 `audio/wav`、`audio/mpeg`、`audio/mp3`。
- Data URI 必须包含逗号后的非空 Base64 内容，且使用标准、完整填充的 Base64 编码。
- 单段音频解码后不得超过 15 MiB；参考音频仍最多 3 段。
- 音频时长和总时长不在前置服务解析，由调用方与私有模型服务继续校验。
- 不接受裸 Base64、本地文件路径、`mm_file://` 或视频 Data URI。

## 4. 验收标准

- 合法 WAV/MP3 音频 Data URI 可创建任务，不再返回 URL 限制提示。
- HTTP/HTTPS 音频 URL 的原行为保持不变。
- 音频 Data URI 在每次首次提交或唯一一次自动重试前上传到对应 Gradio 实例，并以返回的缓存路径构造音频 `FileData`。
- 非法 MIME、空内容、非法 Base64 和超过 15 MiB 的音频在创建任务时返回 400。
- 视频使用非 HTTP/HTTPS URL 时仍提示 `音频视频必须要上传可以访问的url。`。
- 日志不记录 Base64、媒体地址、文件内容或私有缓存路径。

## 5. 不在范围

- 视频 Base64 或 multipart 公共接口。
- 前置服务解析音频时长、采样率、声道或真实文件格式。
- 修改私有模型项目代码。
- 持久化解码后的音频文件。
