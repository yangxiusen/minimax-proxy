# 分辨率档位修正设计

## 背景与目标

当前 API 将短边为 480 像素的生成规格命名为 `768P`，名称与实际尺寸不符。本次修正不增加 `1K`，而是将旧规格改名为 `480P`，新增真正以短边 768 像素为基准的 `768P`，并保留现有 `2K` 档位。

最终 API 只接受 `480P`、`768P`、`2K`。这是一次有意的语义修正：升级后请求中的 `768P` 将生成更高分辨率视频。

## 分辨率映射

| 档位 | 比例 | 宽 x 高 |
| --- | --- | --- |
| 480P | adaptive | 832 x 480 |
| 480P | 21:9 | 1120 x 480 |
| 480P | 16:9 | 832 x 480 |
| 480P | 4:3 | 640 x 480 |
| 480P | 1:1 | 480 x 480 |
| 480P | 3:4 | 480 x 640 |
| 480P | 9:16 | 480 x 832 |
| 768P | adaptive | 1344 x 768 |
| 768P | 21:9 | 1792 x 768 |
| 768P | 16:9 | 1344 x 768 |
| 768P | 4:3 | 1024 x 768 |
| 768P | 1:1 | 768 x 768 |
| 768P | 3:4 | 768 x 1024 |
| 768P | 9:16 | 768 x 1344 |
| 2K | adaptive | 1920 x 1088 |
| 2K | 21:9 | 2560 x 1088 |
| 2K | 16:9 | 1920 x 1088 |
| 2K | 4:3 | 1440 x 1088 |
| 2K | 1:1 | 1088 x 1088 |
| 2K | 3:4 | 1088 x 1440 |
| 2K | 9:16 | 1088 x 1920 |

全部尺寸均为 32 的倍数。`768P` 使用私有 MiniMax H3 项目的默认 `1344 x 768` 作为横屏和 adaptive 基准。

## 配置兼容

示例配置和 Docker 配置增加 `480P`，并将 `768P` 更新为新尺寸。配置校验要求三个档位及其全部比例均存在。

为避免线上外部挂载的旧配置在升级后无法启动，加载器识别以下旧配置形态：不存在 `480P`，且 `768P` 的完整尺寸仍为旧 480 档映射。识别后自动执行一次内存迁移：

1. 将旧 `768P` profile 复制为 `480P`，保留其模型、步数和缓存配置。
2. 将 `768P` 的尺寸替换为新 768 档映射，其他 profile 参数保持不变。
3. 继续执行完整配置校验。

只迁移完整匹配的已知旧映射。其他缺失档位或非法尺寸继续明确报错，避免静默猜测自定义配置。

## API 与任务流

请求校验允许 `480P`、`768P`、`2K`，错误信息同步列出三个值。后续 profile 查找、上游参数映射、任务响应和监控页面继续使用现有通用字段，不新增分支逻辑。

README 和接口规格同步更新允许值及示例，防止调用方继续把旧 `768P` 当作 480 档使用。

## SQLite 迁移

新建第二版迁移，将 `video_tasks.resolution` 的 CHECK 约束扩展为 `480P/768P/2K`。迁移在单个事务内重建 `video_tasks`、复制数据并恢复现有索引。

数据库中升级前的所有 `768P` 任务实际都属于旧 480 档，因此迁移时同时：

- 将 `video_tasks.resolution` 从 `768P` 改为 `480P`；
- 将 `request_json` 顶层的 `resolution` 从 `768P` 改为 `480P`。

这保证排队、运行和恢复中的旧任务在升级后仍使用原来的 480 档 profile。已有请求哈希和幂等记录保持不变，避免升级触发重复任务；在原幂等 TTL 内重放旧请求时仍返回原任务。

新数据库的首版完整结构也直接包含三个允许值。`schema_migrations` 记录版本 2，重复启动不得重复迁移。

## 错误处理与验证

配置升级、数据库迁移任一失败时保持启动失败并返回包含阶段信息的错误，不允许以部分迁移状态继续服务。事务失败必须回滚。

测试覆盖：

- 三个 resolution 的请求接受与未知值拒绝；
- 三个 profile 的完整性和 32 倍数校验；
- 旧外部配置自动迁移为 `480P + 768P + 2K`；
- 自定义非法配置不被旧配置迁移误判；
- 新数据库可写入三个档位；
- 版本 1 数据库升级后，历史字段和请求 JSON 变为 `480P`，索引、任务读取和恢复行为保持正常；
- 完整执行 `go test ./...`、`go vet ./...` 和两个入口构建。

真实上游验证需分别提交至少一个 `480P`、`768P`、`2K` 任务，确认显存占用和输出尺寸符合预期。
